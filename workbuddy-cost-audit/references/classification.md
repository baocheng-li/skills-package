# 任务分类与复杂度分级

消耗台账的筛选栏与「对比建议」都建立在两个标签上：**任务类型**（做什么）和**复杂度层级**（多难）。
（v1.1 起「分类检索」不再作为独立菜单，分类与分级结果直接作为台账字段与筛选维度。）
本文件说明两者的判定规则、为什么这样定、以及为什么在 Agent 场景下需要重新定标。

---

## 1. 任务类型（7 类）

### 1.1 判定顺序

优先级从高到低，**先命中先返回**（不做多标签）：

1. **会话标题**（`sessions.title`）——最可信，是用户自己写的意图；
2. **首条用户指令的前 60 字**——标题为空或泛化时使用；
3. **工具画像兜底**——前两者都没命中关键词时，按「用了什么工具」反推。

### 1.2 关键词表

| 类型 | 关键词（子串匹配，大小写不敏感） |
| --- | --- |
| 抓取监测 | 抓取、爬取、政策、法规、监控、监测、日报、早报、简报、巡检、定时 |
| 应用开发 | 小程序、APP、网页、网站、前端、页面、后台、安装工具、安装包、部署、打包、构建、工具、系统、插件 |
| 代码开发 | 重构、修复、bug、实现、函数、接口、脚本、组件、迁移、升级、改造、代码 |
| 表格处理 | 表格、Excel、CSV、数据清洗、对账、字段、汇总表 |
| 文档生成 | 文档、报告、方案、说明书、周报、纪要、PPT、演示、汇报、建议书、白皮书 |
| 调研分析 | 调研、分析、对比、评估、选型、测算、预算、估值、核查、验证 |
| 多模态生成 | 图片、海报、视频、视觉、logo、插画、封面、配图 |

表内顺序即优先级。「定时」放在抓取监测里，是因为定时任务绝大多数是抓取类；
若你的定时任务是别的用途，**覆盖配置里的关键词表**（见 1.4）。

### 1.3 工具画像兜底

| 工具集合 | 判定 |
| --- | --- |
| 含 `Write` 且不含 `Bash` | 应用开发 |
| 含 `Write` / `Edit` / `NotebookEdit` / `MultiEdit` 且含 `Bash` | 代码开发 |
| 含 `Bash` / `PS` | 代码开发 |
| 含 `WebSearch` / `WebFetch` / `domain_search` | 调研分析 |
| 含 `Read` / `Grep` / `Glob` | 调研分析 |
| 都不满足 | 通用任务 |

> 兜底是**最后手段**：工具画像只能说明「怎么做的」，不等于「要做什么」。
> 报告里 `通用任务` 占比高，说明标题与指令都不足以为分类提供依据，应把它当作数据质量问题看。

### 1.4 覆盖关键词表

改 `config/classification.json` 的 `task_types`，数组顺序即优先级：

```json
{
  "task_types": [
    {"name": "抓取监测", "keys": ["抓取", "政策", "法规"]},
    {"name": "我的自定义类型", "keys": ["关键词A", "关键词B"]}
  ]
}
```

生效方式：`audit.py` 在解析前调用适配器的 `set_type_rules()` 覆盖内置表，
运行时日志会打印 `任务类型关键词表已由配置覆盖：N 类`。
**注意**：覆盖是整体替换，不是追加；想保留内置类就必须把它们一起写进配置。

## 2. 复杂度分级（L1—L4）

### 2.1 分级依据

**模型步数**（`nModelSteps`），即该任务中 `kind=model` 的步骤数。不用 token、不用积分，
因为这两者受模型单价影响，换模型就会漂移，无法跨时间对比。

### 2.2 两套档位

#### `spec`（默认，来自 BRD）

| 层级 | 模型步数 | 典型形态 |
| --- | --- | --- |
| L1 | 0—3 | 单轮问答、一次查询 |
| L2 | 4—8 | 带少量工具调用的任务 |
| L3 | 9—15 | 多轮工具编排 |
| L4 | ≥16 | 长链路 Agent 任务 |

#### `quantile`（按本机分布重定标）

```
切成三段：25% 分位 → L1 上界；60% 分位 → L2 上界；85% 分位 → L3 上界
超出 85% → L4
```

启用：`--complexity-profile quantile`，或在 `config/classification.json` 把 `profile` 改为 `quantile`。

### 2.3 为什么需要 quantile

固定阈值的前提是「步数分布集中在 L2—L3」。Agent 长任务的实际分布不是这样：

- 真实数据里 **73% 的任务落在 L4**（110 个任务中 80 个）；
- 这意味着 L4 里既有 16 步的小任务，也有 200 步的巨任务，**分级失去分辨率**；
- 后果是 F7 的「层级 × 模型对比」几乎全在 L4 一个格子里，模型建议没有区分度。

因此当 `L4 占比 > 60%` 时：

1. `classification.note` 自动写入提示：

   > 固定步数阈值下有 73% 任务落在 L4，分级分辨率不足；可用 `--complexity-profile quantile` 按本机分位重定标。

2. F7 第三档（结构性优化）自动生成一条「重定标任务复杂度分级」建议。

### 2.4 分级结果字段

| 字段 | 说明 |
| --- | --- |
| `level` | `L1`—`L4` |
| `levelBasis` | 判定依据，形如 `steps=12`，便于复核 |
| `classification.profile` | 本次使用的档位（`spec` / `quantile`） |
| `classification.bounds` | 三个上界值（L1/L2/L3 的步数上限） |
| `classification.levels` | 各层级任务数 |
| `classification.l4Share` | L4 占比 |
| `classification.note` | 分辨率不足时的提示 |

## 3. 项目归属

判定链：`sessions.cwd` → `plugin_context_json.projectResources` → `session.project_id`。

三者都取不到时映射为 **`未绑定项目`**。

### 为什么不猜

早期实现尝试从 `cwd` 的父目录名反推项目（如 `~/WorkBuddy/20261026-abc` → 取 `abc`），
但真实 cwd 多为时间戳工作区，反推出来的名字对用户没有意义，反而制造「看似有项目维度」的假象。

因此现行策略是：**取不到就标未绑定，并给出占比**。

`classification.unboundProjectRate` 会直接写进报告，例如：

> 未绑定项目占比 81%：`cwd` 为时间戳工作区，无法反推项目名。建议在会话中显式绑定项目后再看项目维度。

`config/classification.json` 的 `project_aliases` 可做名称归一（把多个同义项目名映射为一个），
但不会把 `未绑定项目` 变成真实项目。

## 4. 触发方式

| `trigger` | 判定来源 |
| --- | --- |
| `定时` | `automations` 表能匹配到该任务 |
| `后台自动化` | `sessions.is_background_automation = 1` |
| `人工` | 其余 |

`triggerType` 为其英文枚举：`scheduled` / `auto` / `manual`，供前端筛选。

## 5. 过滤与检索

`query.py` 支持 5 个维度组合过滤（AND 关系）：

```bash
--project <name>        # 精确匹配，别名已归一
--task-type <name>      # 7 类之一
--level L1|L2|L3|L4
--from 2026-09-01 --to 2026-09-30
--last 7d|30d           # 相对窗口，与 --from/--to 互斥
```

过滤后会**重新执行一遍分类汇总**（项目维度、类型×层级矩阵、L4 占比都会按筛选结果重算），
因此报告里看到的矩阵与 KPI 始终是同一口径。

`--days N` 与 `--last Nd` 的差别：`--days` 是「从今天往前 N 天」，`--last` 是对 `--days` 的语法糖，
但 `--last` 会同时作为 `query.parse_range` 的锚点，在只看定时任务时更直观。

---

## 6. 分类质量的自我检查

监控审计舱会显示两条提示条件，任一触发都说明分类结果需要谨慎解读：

1. **L4 占比 > 60%** → 分级分辨率不足，建议 `quantile`；
2. **未绑定项目占比 > 50%** → 项目维度不可用，不要基于项目做归因。

这两条是**数据质量问题**，不是工具缺陷。工具的责任是把问题显性化，而不是掩盖它。
